## 遇到的问题与根因

1. `mvn clean test` 首次未进入测试。指定缓存缺少 `maven-clean-plugin:3.4.1`，沙箱禁止访问 Maven Central，报错 `Permission denied: getsockopt`。获得受限外部依赖访问后重跑并通过；首次基础设施失败没有被标记为测试结果。
2. `mvn clean package` 首次缺少 `maven-jar-plugin:3.4.2`，同样被沙箱网络策略阻止。获得受限访问、填充同一临时缓存后重跑并通过。
3. Task 9 的首次依赖安装被中断，导致原生 Vite binding 截断，根因是未完整写入的 `node_modules`；重新执行同一批准的安装流程后类型检查和构建通过。
4. Task 9 生产构建保留单个大于 500 kB 的 chunk 告警。它是非阻塞体积告警，不影响本阶段构建结果；后续真实页面拆分时再处理。
5. Task 10 第一次 MySQL 轮询中，PowerShell 将预期的首次连接失败 stderr 提升为终止错误；确认根因后改为只判断 `mysqladmin` 的 exit code。
6. 后续轮询在控制进程中断时，隔离 MySQL 已实际 ready。通过 server error log、精确 PID/端口和 `mysqladmin ping` exit `0` 确认后，从同一实例继续，未重初始化或回退到 3306。
7. MySQL shutdown 后端口先于进程完全退出，第一次删除 datadir 因 redo 文件仍被占用而失败。等待精确 PID `6152`、`14900` 全部退出，重新验证绝对路径、父目录和前缀后删除成功。
8. Docker 缺失。V0.1 使用直接、隔离的 MySQL 8.4.7 验证，不依赖 Docker，因此不阻塞。
9. 最终代码审查发现 Spring Boot 默认用户自动配置会在测试和普通启动时记录完整随机安全密码。证据是修复前 Surefire 报告中的 `Using generated security password`；通过 RED 测试复现 `inMemoryUserDetailsManager` 后，最小排除 `UserDetailsServiceAutoConfiguration`，并以 18 项完整测试和日志扫描验证修复。审查同时发现 `BusinessException` 可被子类覆写客户端消息，因此将其声明为 `final` 并增加反射回归测试。
10. 审查修复后的主会话首次重跑 Maven Clean 时，受限沙箱无法删除既有 `target`，报错 `Access is denied`；其中一次还捕获到并行审查 JVM 对同一输出目录的争用。停止并行构建后，受限上下文仍无法完成 Clean，因此没有绕过或跳过测试，而是在用户明确批准只清理和重新生成 `stockmentor-backend/target` 后，以离线 Maven 模式分别重跑 `mvn clean test` 与 `mvn clean package`，两条命令均 exit `0`。
