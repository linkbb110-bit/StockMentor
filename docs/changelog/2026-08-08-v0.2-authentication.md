## 实现内容

### 注册与登录

- 注册和登录先通过 `EmailNormalizer` 对邮箱 trim、转小写并执行最终格式/长度校验；昵称由共享 `NicknameNormalizer` 先 trim 再校验。
- 密码保持原值语义，不自动 trim；在原有 8–64 字符规则之外统一要求不超过 72 UTF-8 字节，只以 BCrypt 哈希写入 `sys_user.password_hash`。DTO 与 Service 在账户查询或 BCrypt 之前拒绝超限输入，恰好 72 字节仍可编码与登录。
- 注册默认创建 `USER`、`ACTIVE` 用户，更新首次 `last_login_at` 成功后才签发 Token 并返回 HTTP 201。
- 登录成功更新 `last_login_at` 后返回 HTTP 200；错误密码与不存在邮箱都返回 HTTP 401、`AUTH_INVALID_CREDENTIALS` 和相同公共消息。
- 数据库唯一索引 `uk_sys_user_email` 是并发重复注册的最终保护，并映射为 HTTP 409。

### JWT 与 Spring Security

- JWT 使用 Spring Security OAuth2 JOSE、HS256 和 7200 秒默认有效期，只包含 `sub`、`iat`、`exp`、`jti`。
- `JWT_SECRET` 只能来自环境变量；缺失或不足 32 字节时启动失败，不自动生成密钥。
- `JwtAuthenticationFilter` 每次受保护请求按 Token 用户 ID 重查数据库状态和最新角色；禁用或逻辑删除用户的旧 Token 立即失效。
- Security 使用 `STATELESS`，关闭 Form Login 与 HTTP Basic，提供统一 JSON 401/403；CORS 仅接受 `CORS_ALLOWED_ORIGINS` 的显式白名单。

### 当前用户与前端行为

- `GET /api/v1/users/me` 返回 `id`、`email`、`nickname`、`role`、`createdAt`，不返回密码哈希、内部状态或 Entity。
- `PATCH /api/v1/users/me/nickname` 只按当前认证用户 ID 更新并返回最新资料，不能修改邮箱、角色或状态。
- 前端提供 `/login`、`/register`、`/dashboard`、`/profile`；认证占位首页不显示未实现的学习统计。
- Pinia 在启动时恢复并验证会话；`sessionStorage` 只保存 `stockmentor.accessToken` 和 `stockmentor.currentUser`，新增的 authentication generation 仅驻留内存。
- 登录/注册、`/users/me`、昵称和 401 都捕获 Token + generation 所有权；旧异步完成不能覆盖或复活新会话，旧 401 不能清除新会话，同一当前所有权的并发 401 仍只处理一次。登录失败 401 不产生重定向循环；退出仅清理本地状态并推进 generation。
- 登录和注册邮箱输入移除原始 DOM `maxlength=254`；trim 后的格式与最大 254 字符校验保持不变，因此带两侧空格、规范化后恰好 254 字符的合法邮箱不会被浏览器提前截断。

## 遇到的问题与根因

1. `mvn.cmd` 不在当前 PATH；根因是本会话命令解析环境。使用实际存在且已验证的 IntelliJ Maven 绝对路径，没有修改产品。
2. 首次后端聚焦测试在读取本地 Maven 缓存 JAR 时收到 `Access is denied`；根因是沙箱/缓存访问边界，不是编译或行为失败。该次未进入测试；权威 Java 17 RED 运行得到 55 tests、5 个预期失败，随后 GREEN 与全量门禁均通过。
3. Spring Security Crypto 6.5.11 的实际行为与最初上游特征假设不同：73 字节候选与相同前 72 字节哈希执行 `matches` 返回 `true`，证明 BCrypt 前缀截断风险。更正的特征测试没有放宽产品要求；登录仍在账户查询与 BCrypt 之前拒绝超限输入。
4. ignored 运行器先更新精确工作树/JAR 与字节边界 HTTP 断言；启动前的第二次审查发现还需显式覆盖要求中的 5173 和 72/73 字节形状门，因此在没有启动任何运行实例前完成第二次 ignored-only 修正。唯一一次权威运行 exit 0，不存在失败运行或重复运行。
5. 工作树包含审查要求的产品修复，但按重审边界未 stage、commit、push 或 merge；HEAD 因此保持最终修复开始时的 `4a15f8cefc81060c3c0fc00000855cec046e6781`。
